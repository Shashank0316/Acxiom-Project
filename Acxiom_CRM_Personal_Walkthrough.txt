=========================================
AcxiomCRM - Personal Walkthrough & Guide
=========================================

Hey! This is the "behind the scenes" guide just for you. It explains exactly how we built this CRM, why we made certain choices, and how the different pieces connect. Use this to understand the code so you can confidently talk about it. (Be sure to delete this file before submitting/showing the repo!)

1. HOW THE ARCHITECTURE WORKS
-----------------------------
We used a standard ASP.NET Core MVC (Model-View-Controller) pattern. 
- Models (`/Models/DomainEntities.cs`): This is where we define what a Lead, Customer, or Opportunity looks like in C#. We put tags like `[Required]` or `[EmailAddress]` on them. This is amazing because it tells Entity Framework how to build the database tables AND tells the frontend how to validate forms automatically.
- Views (`/Views/`): The HTML/CSS pages using Razor (`.cshtml`). We used standard Bootstrap to make it look clean.
- Controllers (`/Controllers/`): The "brain" that connects the UI to the database. When someone clicks "Save" on a form, the Controller receives the data, checks if it's valid, and saves it.

2. HOW WE SECURED IT (AUTHORIZATION)
------------------------------------
You'll see `[Authorize]` at the top of almost every controller. This stops unauthenticated people from seeing anything.
But the really cool part is the Row-Level Security we built. In every controller, we made a helper function called `GetAuthorizedQuery()`. 
What it does: 
If the logged-in user is an Admin or Manager, it returns `_context.Leads` (everything). 
But if the user is a "Sales Executive", it appends `.Where(l => l.AssignedToId == userId)`.
Why we did it this way: Instead of writing that `if` statement 50 times in every single GET, Edit, and Delete method, we funnel all database reads through that one function. It guarantees a Sales Exec can NEVER see another person's lead.

3. THE API AND DTOs
-------------------
We created an API inside `Controllers/Api/`. 
Why did we use DTOs (Data Transfer Objects) like `CreateLeadDto` instead of just using the `Lead` model?
Imagine our `Lead` database table has a secret column called `IsPremium`. If we let the API bind directly to the `Lead` model, a hacker could send `{ "LeadName": "John", "IsPremium": true }` in their POST request, and our system would save it! (This is called an Over-posting attack).
By creating a `CreateLeadDto` that ONLY contains safe fields (Name, Phone, Email), we completely block that attack. We map the DTO data to a real `Lead` object manually in the controller.

4. LEAD CONVERSION (THE TRICKY PART)
------------------------------------
When a Lead is converted, three things have to happen at the exact same time:
1. Make a new Customer record.
2. Make a new Opportunity record attached to that Customer.
3. Change the original Lead's status to "Converted".
What if the database crashes halfway through? We'd have a Customer but no Opportunity.
How we fixed it: We put this logic in `/Services/LeadConversionService.cs` and wrapped it in a Database Transaction (`BeginTransactionAsync`). A transaction says "Do all 3 things, or do NOTHING." If anything fails, it rolls the database back to exactly how it was. We also wrote tests specifically to prove this rollback works.

5. THE DASHBOARD (CHART.JS)
---------------------------
The PDF asked for Chart.js. In `HomeController.cs`, we query the database to count how many leads are in each status (New, Qualified, etc.) and calculate the financial value of Opportunities at each stage.
We put that data into `ViewBag`, and then in `Views/Home/Index.cshtml`, we wrote a small Javascript block using Chart.js that pulls those `ViewBag` arrays into the pie chart and bar chart.

6. AUDIT LOGGING
----------------
Every time we do `_context.Add()` or `_context.Update()` in the controllers, right before we call `_context.SaveChangesAsync()`, we add a new `AuditLog` row to the database. We log the user's ID, what they did ("Create" or "Update"), and what entity they touched. It's simple but highly effective for compliance.

7. HOW TO EXPLAIN THE TESTS
---------------------------
If they ask about testing, tell them you used an **In-Memory SQLite Database**. This is a massive flex. It means our tests don't just mock things; they actually spin up a real, temporary SQL database in RAM, run the EF Core queries to test the real authorization and transaction logic, and then destroy the database in milliseconds. It proves the logic actually works at the SQL level, not just in C#.
